transfer-qr — END-TO-END INTEGRATION (S0..S5 in one pass)
=========================================================

Chain: file -> chunk+gzip+manifest -> RaptorQ -> header+CRC -> cells ->
       fiducials -> [ Channel::*_handheld() ] -> rectify -> CRC -> fountain
       -> BLAKE3 per chunk -> write at offset -> whole-file BLAKE3.
Nothing is stubbed: the fountain is raptorq (ADR-0004), not the S5 repeater.

Layers are the clean rungs S4 measured (artifacts/s4-frontier.csv):
  good_handheld    P8 @  8px   capacity   8748 B/frame   grid 216x111
  webcam_handheld  P8 @  8px   capacity   8748 B/frame   grid 216x111
  potato_handheld  P8 @ 20px   capacity   1182 B/frame   grid 83x41

REAL END-TO-END THROUGHPUT
--------------------------
KB/s is delivered file bytes / (frames emitted / FPS). FPS is ASSUMED —
nothing here measures a screen or a camera. `cpu KB/s` is a different number:
delivered bytes / summed single-thread CPU on each side, all in KB/s.

  cpu dec(refit)  — re-solving the geometry on EVERY frame. This is the
                    pre-ADR-0015 path and is NOT the decoder's real cost.
  cpu dec(cached) — ADR-0015: fit once, reuse the pose, re-fit only when a
                    frame fails. Still warps the whole frame (ADR-0015's
                    sample-point warp is not implemented here), and the
                    simulator holds the pose perfectly still, so it is an
                    upper bound on cache hit rate — a real hand moves.

  `channel ms` is the simulator standing in for air+sensor. It is NOT a cost
  either device pays in production; it is excluded from cpu KB/s above.
  `encode ms` is the per-frame sender cost (render + fiducials) only. Chunking,
  gzip and the manifest hashes happen once, outside the frame loop — S5 measured
  the compressor at 81.2 MB/s, ~600x the fastest channel here (ADR-0014).
  `fit ms` is every-frame geometry; `fit chg ms` is what ADR-0015 actually pays
  (acquisition + re-fits). `decode ms` is `header::decode_frame` — CRC, symbol
  sampling, bit unpacking — the only part that is really "decoding".

LAYERED BROADCAST — ONE STREAM, BOTH CAMERAS (ADR-0011, ADR-0012)
-----------------------------------------------------------------
  chunk 65536 B, symbol 1178 B (the coarse rung), K = 56 packets.
  coarse frame (P8@20px) carries 1 packet = 1182 B; dense frame (P8@8px) carries
  7 packets = 8274 of 8748 B (94.6% — the granularity cost of a shared symbol size).

  camera               frames    coarse  dense used     packets   B/frame
  good_handheld            11         3           8          59      5958
  potato_handheld         221        56           0          56       297

  Both cameras finish off ONE broadcast, and the good camera's coarse frames are
  not wasted airtime — they carry packets of the same source block. With a
  per-layer symbol size (what ADR-0011 implies) they would have been unusable.

HUMAN-FACING GUARANTEES (ADR-0005 / ADR-0011)
---------------------------------------------
  1. display code   sender C4B9TF == receiver C4B9TF   -> MATCH
  2. needed_more()  starts at 217, ends at 0, 218 readings, monotone=true
     first ten: [217, 216, 215, 214, 213, 212, 211, 210, 209, 208]   last ten: [9, 8, 7, 6, 5, 4, 3, 2, 1, 0]
     a human reads a 1-3 digit integer; the largest seen anywhere here is 217.

  3. killed at 23/32 chunks (71.9% = 6029312 of 8388608 B on disk). Receiver screen: "Q-7C"
     typed back as "q-7c" -> chunk 23 need 7; 23 retained chunks re-read off the sink and re-verified
     re-sent 9 chunks in 99 frames (28.1% of a fresh transfer); byte-identical: true; whole-file BLAKE3: true

  4. hopeless camera: 15 frames tried, any decode = false, gave up after 1.00s of
     simulated capture (4621 ms of real CPU). rectify() returns None (no fiducials),
     so the UI can say "cannot see the code — move closer / clean the lens" at frame 15,
     never hang at 0%.
