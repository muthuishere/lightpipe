The measured numbers

Everything here comes from a spike that anyone can re-run, and leaves an artifact anyone can look at. Where a figure is an assumption rather than a measurement, it says so.

One caveat covers this entire page.

All optical figures were produced against a channel simulator, not hardware. No real camera has yet decoded a real screen in this project. See Status & limits.

S2 · artifacts/s2-integrity.txt. Corruption swept from one symbol up to 30% of every cell in the frame. The 309 accepted frames had their corruption land entirely in padding outside the CRC-covered bytes, and every one returned exactly the right data. Not one corrupt payload was ever presented as truth.

End to end, the human-facing guarantee: the sender's six-character display code and the receiver's matched, and the “need more” counter fell monotonically from 217 to 0 across 218 readings. The largest integer a human would have had to read anywhere in that run was 217.

S5 · artifacts/s5-pipeline.txt. Peak memory is a real getrusage high-water mark taken in a re-executed child process, not an assertion. Memory tracks chunk size, never file size.

Two results worth keeping:

  • The “1–3% chunking penalty” belongs to 256 KB, not to chunking. At 64 KB it is 10–11%, because gzip's window is only 32 KB and a 64 KB chunk spends half its length warming up a dictionary it then throws away. Nothing may shrink the chunk below 256 KB to chase latency without re-running that measurement.
  • Compression is never on the critical path. The compressor runs 600× to 4,500× faster than the channel it feeds. An earlier design tested the first chunk and skipped gzip for incompressible input; that saved 258× the CPU of a resource with three orders of magnitude of headroom, and bought a branch, a flag and two code paths with it. It was removed. Everything is now always chunked and always gzipped — incompressible input gets 0.02% larger, which is 26 bytes on a 128 KB blob, against a channel that already spends 26% of itself on corner markers.

Clean decode survives the whole ±40° in-plane rotation range that was swept, 35° yaw, 17° pitch, and barrel distortion to k = −0.20.

S4 · artifacts/s4-warped.png, artifacts/s4-rectified.png, artifacts/s4-frontier.csv.
The finding that changed the product.

Rotation is not what costs you throughput — the decoder is clean to ±40°. Framing is. A 16:9 screen rotated 15° needs more sensor height than it has, so it can only fill 68% of the view, and lost screen area is lost resolution. That is why the app asks you for a Screen shape and why “move closer” is the first troubleshooting step: the rectifier is essentially exact, but a 6-pixel cell that arrives as 3 sensor pixels cannot be read by anything.

S7 · docs/contracts/wasm-api.md, docs/adr/0007-rust-core-wasm-browser-only.md. Node 24, M-series Mac, median of 5 runs. Zero-copy is verified rather than claimed: 500 consecutive frames grow WebAssembly linear memory by 0 bytes, where a copying boundary would have moved 4.0 GiB.

The decoding is sixty times faster than needed. Everything slow is geometry, and the fix is to stop re-solving it — the decoder caches the pose it fitted and re-fits only when a frame fails. In the end-to-end run, the pose was acquired once and never re-fitted at all except on the frames a simulated rolling-shutter tear destroyed. That figure is an upper bound on the cache's value: the simulator holds the camera perfectly still, and a real hand does not.

Numbers that are not on this page

  • Any real camera reading any real screen. Nothing. The hardware spike is open.
  • Frame rate. Every KB/s above divides a frame count by an assumed 15 or 30 FPS. Neither has been measured against a real screen and a real sensor.
  • Screen tearing between an unsynchronised refresh and a camera shutter. Not modelled in the simulator, and prior art suggests frame synchronisation alone can nearly double throughput — likely the single largest remaining unknown.
  • Auto-exposure and autofocus hunting against a changing image. Not modelled.
  • Screen moiré and a real JPEG DCT (the simulator uses a crude 8×8 block-mean stand-in). Not modelled.
  • The screen-capture path's 2.65 MB/s. Reported by the app and quoted in the CLI documentation, but with no artifact in artifacts/ behind it.
