A file that crosses as light

One screen animates a grid of coloured cells. The other device's camera watches it. The file arrives. No network, no Bluetooth, no NFC, no pairing, no cable — at any point.

There is nothing to connect and nothing to trust. The two devices never exchange an address, a key or a handshake; the only thing that crosses between them is photons. That is the entire point, and it is also the entire limitation.

When to use it — and when not to

lightpipe is for small things that matter: an SSH or age key, a signed transaction, a wallet seed, a .env, a config file, a certificate, a PDF, a screenshot, a note, a snippet of text. It is not for video, disk images or photo libraries.

Here is why, in the project's own measured numbers. The optical channel carries, hand-held at 15 frames per second:

receiverbytes per framethroughput
good phone or webcam, hand-held8,748128.9 KB/s
weak “potato” webcam, hand-held1,18217.6 KB/s
Per-frame figures: S4 warped clean-decode frontier (artifacts/s4-frontier.csv, docs/spikes/PLAN.md). Throughput: end-to-end integration run on a 1 MB incompressible blob (artifacts/e2e-report.txt), at an assumed 15 FPS — nothing in the repo has yet measured a real screen against a real camera.

So take one minute of 1080p phone video, roughly 100 MB:

attime to send 100 MB
128.9 KB/s (good camera)about 13 minutes
17.6 KB/s (weak webcam)about 95 minutes

Sixty seconds of video costs between thirteen minutes and an hour and a half of holding a camera steady. That is not a bug to be fixed later; it is what a screen and a lens can carry. Send the key, not the movie.

If you only want a file off your laptop and onto your phone, use qrcp.

qrcp serves the file over your Wi-Fi and shows a QR code pointing at it. It is excellent, it is far faster, and lightpipe is not trying to replace it. Reach for lightpipe when the network is the thing you are not allowed to use: USB banned, radio banned, an air-gapped machine, a device you do not want to join to anything.

Quick start — the hosted app

Nothing to install. Open the app on both devices.

  1. On the sending device, press Send. Drop a file on the panel, choose one, or press ⌘V / Ctrl+V to send whatever is on your clipboard. There is also a Text / note tab — untyped text goes as markdown and is rendered on the other side.
  2. Two settings sit under the file picker:
    • Reliability vs speed — from Most reliable (slowest) through Reliable, Balanced, Fast, to Fastest (needs a great camera). Auto — pick for me is the default and is a safe middle setting. Settings the engine cannot actually round-trip in this build are greyed out rather than offered.
    • Screen shape — Auto — match this device, Landscape (1920 × 1080, for a laptop camera), Portrait (1080 × 1920, for a phone held upright), or Fill this screen exactly. This is not cosmetic: whatever fraction of the camera's view the sending screen fails to fill is throughput thrown away, so the picture should be the shape of the thing looking at it.
  3. Check the Manifest panel. It shows the name, the type, the size on the wire, the chunk count, and a display code — six characters. Memorise it or leave it on screen; it is the whole integrity check.
  4. Press Start sending, then Full screen. The screen now animates. It will keep animating until you stop it — the sender has no idea whether anyone is watching.
  5. On the receiving device, press Receive. Under Where are the pixels coming from? pick Camera — point it at the other screen, then Start receiving and allow camera access.
  6. Fill the camera's view with the sending screen. Watch the picture quality bar — it tells you plainly whether you are sharp (“Sharp. Hold it there.”) or need to move closer. Then watch need more count down.
  7. When the receiver reads COMPLETE ✓ followed by six characters, compare those six characters with the sending screen. If they match, what arrived is byte-for-byte identical. If they do not, throw it away and start again. Then press Save — and stop the sender.
No hardware? Try the Loopback demo tab first.

It runs both halves in one tab: the receiver reads the sender's own canvas through a shrink-and-blur stage that stands in for a camera. Every step is real — frames, unreadable frames, pieces completing, the final code comparison. It is the fastest way to understand what you are about to do with two real devices. Under Pretend the camera is you can pick anything from Good phone camera down to Too bad to read.

Quick start — the CLI, fully offline

The CLI serves the entire app — React bundle and the Rust/WebAssembly core — from files inside the npm package. No CDN, no fetch, no update check, no telemetry. Unplug the machine and it behaves identically.

npx lightpipe send report.pdf      # serve, open a browser, start broadcasting
npx lightpipe send --text "hi"     # a literal string, sent as markdown
cat notes.md | npx lightpipe send  # stdin
npx lightpipe receive camera       # capture from the webcam (the default)
npx lightpipe receive screen       # capture a screen or window
npx lightpipe receive --out ./in   # write the finished file straight to disk
npx lightpipe serve                # just serve; choose a mode in the browser
Not published to npm yet.

cli/package.json declares lightpipe at version 0.1.0, but there is no publish step in this repository's CI and no release has been cut, so npx lightpipe will not resolve today. Build it from the repo instead:

npm --prefix cli install
npm --prefix cli run build     # produces cli/public/
node cli/bin/lightpipe.js send report.pdf

camera permissionone click, the first time an origin asks
receive screenone click, then the OS window picker. getDisplayMedia will not open without a real gesture
Source: cli/README.md, docs/cli.md.

No certificates, ever

http://localhost is already a secure context, which is all that getUserMedia and getDisplayMedia require. A desktop can send or receive there with no TLS at all; a phone uses the hosted HTTPS site. So lightpipe generates no certificate, creates no certificate authority, and never writes a private key anywhere. --https --cert --key exists only to serve a certificate you already have.

receive --out <dir>

The one thing only the CLI can do: the page posts the finished file back and the CLI writes it to disk — no download dialog. It is off unless you ask for it, loopback-only by default, gated by a per-run 24-byte token, the filename is reduced to a single harmless path segment, nothing is ever overwritten, and the bytes are checked against a SHA-256 the page reports before anything is written.

Be clear about what that SHA-256 covers: it verifies the transport hop, page to disk. It is not the optical integrity check. The six-character display code, which you compare by eye against the sending screen, is.

Two ways to receive — and which one to want

The app offers three sources under Where are the pixels coming from?: Camera, Screen or window, and Built-in demo. The first two are real, and they are not close to each other in speed.

pathreported ratewhy
Screen or window capture2.65 MB/spixel-perfect grab: no lens, no perspective, no lighting, no chroma subsampling. The decoder samples the grid where it knows the grid is
Camera125.8 KB/sa lens, a pose and a hand — every frame has to be located and geometrically corrected before a single byte is read
Reported in docs/cli.md and printed by the CLI (cli/src/cli.js) as the app's own measured figures. Unlike every other number on this site, these two have no artifact in artifacts/ backing them — treat them as live app readings, not as a spike result.

Roughly a 21× difference, and the reason is not mysterious. Profiling the compiled wasm decoder at 1920 × 1080 found that the actual decoding — CRC, symbol sampling, bit unpacking — costs 0.55 ms per frame, about 1,816 FPS. Everything expensive is geometry: finding the four corner markers (8.2 ms), fitting the pose and lens term (30.6 ms), warping the frame (20.1 ms). A screen capture skips all of it.

Source: docs/adr/0015-cache-the-homography.md, docs/contracts/wasm-api.md.
The case where this is the right tool, not a curiosity.

You are on an air-gapped or locked-down machine and you reach it over VNC, RDP or a KVM-over-IP console. Files cannot leave it — no share, no clipboard, no USB. But you can see its screen. Run the sender there, and on your own machine capture the remote-desktop window directly: lightpipe receive screen, or the Screen or window — capture it directly source in the app. The bytes leave through the pixels you were already allowed to look at, at the pixel-perfect rate rather than the camera rate.

Two things to get right when the picker appears: share the window that is showing the code (or the whole screen it sits on), and make sure nothing is covering it — anything on top of the code is a hole in the picture. Your browser will show its own “you are sharing your screen” indicator; that is normal and cannot be turned off.

There is a checkbox, Skip the alignment search (faster), on by default for this source. It assumes the captured pixels are a one-to-one copy of the sending screen. If the window is scaled or windowed and nothing decodes, the app turns the search back on by itself and tells you it did.

If you are receiving by screen capture, the sending side can safely use its Fastest setting. Only do that if the other side really is capturing a screen — a camera will not keep up.

How it works, in one screen

  • chunkthe file is split into 256 KB pieces
  • gzipevery piece compressed on its own
  • fountaineach piece becomes an endless stream of distinct blocks
  • cellsblocks packed into a grid of coloured squares
  • framesgrid drawn with corner markers and a colour reference row
  • camerathe other device watches the screen
  • decodefind the grid, read the cells, rebuild the piece, write it

Four ideas carry the whole design:

  • Chunking makes progress real. Each piece is compressed and coded on its own, so memory stays bounded and a transfer that dies at 70% keeps 70% of the work. Measured: a 1 GB file transfers with a 4.6 MB peak memory footprint — 0.0045× the file size.
  • Fountain coding makes lost frames normal. The sender emits an endless stream of distinct coded blocks; the receiver rebuilds a piece from any N of them, in any order. A blurred, torn or missed frame is not an error path, it is Tuesday. Measured cost of the coding itself: across 3,600 decodes at drop rates from 0% to 70%, 99.69% needed exactly the minimum number of blocks and the worst case anywhere needed one extra.
  • There is no back-channel. Because the stream is rateless, the receiver never has to say which blocks it missed — only how many more. That is one small integer a human can read off a screen. It also means the sender is blind: it cannot know whether anyone is watching, so it loops forever and you stop it.
  • A bad frame is dropped, never believed. Every frame carries a 25-byte header with a CRC32. If it does not validate, the whole frame becomes an erasure — which the fountain layer already handles perfectly. Measured across 101,000 deliberately corrupted frames: zero false accepts. Not one corrupt payload was ever presented as truth.

It is not QR. QR spends most of its area on finder patterns, timing patterns and alignment blocks so a phone can read a crumpled poster at an angle. lightpipe has a flat, self-illuminated screen at a fixed distance, so it uses a format built for that channel instead.

If you want the real depth — why the palette is the corners of the RGB cube, why symbol error rate is non-monotonic in cell size, how a lens distortion term nobody can observe from four points is recovered anyway — the project keeps thirteen standalone explainers in docs/principles/, and a decision record for every option it closed in docs/adr/. The Numbers page here collects what has actually been measured.

What to expect, and what to do when it stalls

Expect this — it is not going wrong

  • Frames that do not read. The unreadable counter goes up and the app labels it “fine”, because it is. The picture repeats.
  • The sender showing no progress at all. It genuinely cannot know. All real status lives on the receiver.
  • The sender never stopping. By design. Stop it yourself when the receiving screen reads COMPLETE.
  • A tiny file showing a still image instead of an animation. If the whole payload fits in one picture, animating it would only make it harder to catch, so the app holds it.

If the receiver is not decoding

  • Fill the frame. This is the single biggest lever. The geometry work measured that a hand-held camera framing the screen at 80% and slightly off-axis is where the throughput goes — a 6-pixel cell that arrives as 3 sensor pixels is unreadable. Move closer until the sending screen fills the view.
  • Go fullscreen on the sender. Same reason. It is one click.
  • Hold steady, and get light on it. Watch the picture quality bar rather than guessing: above 75% it says “Sharp. Hold it there.”
  • Kill glare and reflections. A glossy panel bouncing a lamp back is a hole in the picture.
  • Turn off macOS Center Stage. This one is specific and it will waste your afternoon otherwise. Center Stage re-frames the camera by itself, mid-transfer. The decoder caches the geometry it solved on the first frame and reuses it precisely because the camera is not supposed to teleport between exposures; a silent re-frame invalidates that cached pose, and the transfer stalls until it re-fits. Same logic applies to any auto-framing or “follow me” camera feature.
  • Turn off Night Shift, f.lux, and any blue-light filter on the sending screen. Every frame carries its own colour reference row, but a global colour cast is still the wrong thing to hand it.
  • Fix the display brightness. Auto-brightness is a slow gain drift that nothing downstream can see coming.
  • Drop the speed setting. Most reliable (slowest) uses the biggest cells. It is slower and it finishes; that trade is the whole point.
  • If nothing decodes at all, the app says so out loud within seconds — “This video source is too low-resolution to read the code from” or “Nothing is decoding” with a frame count. It is designed to fail loudly rather than sit at 0%.

Reading the receiver

  • need more — the only number that matters. It should fall. It is the count of coded blocks still wanted for the piece in flight, and it is the one integer a human would ever have to relay.
  • pieces done — chunks finished out of the total. The little grid below the progress bar shows which.
  • unreadable — frames dropped on CRC. Expected. Free.
  • already had — duplicate blocks. Harmless.
  • display code — six characters, at the end. Compare it with the sending screen. Nothing travels back the other way, so that eye comparison is the integrity check, not a nicety.

Before you rely on this

The project's culture is measurement, and it publishes what it has not measured as loudly as what it has. Two things you should know before trusting lightpipe with anything real:

No real camera has ever decoded a real screen.

Every number above the screen-capture row comes from a channel simulator — a deliberately good one, with perspective warp, defocus, chroma subsampling, white-balance drift, sensor noise, MJPEG artifacts, frame drops and rolling-shutter tear — but a simulator. The spike that captures real webcam fixtures and measures how wrong it is (S6) is written up, takes about ten minutes and no code, and is still open. Frame tearing between an unsynchronised screen refresh and a camera shutter, and auto-exposure hunting, are not modelled at all.

The full verified-versus-not accounting is on the Status & limits page. Read it. It is short and it does not flatter the project.
