Status and limits

What is verified, what is not, and what simply does not exist yet. Nothing on this page is softened.

Verified

55 passRust core tests. cargo test --workspace — palette, bit codec, frame geometry, modem, channel simulator, fountain, header, pipeline. No hardware, no browser.
87 passWebAssembly harness checks. node harness/run.mjs runs the whole chain through the compiled wasm in Node, including a byte-identical round trip and the zero-copy claim proved by checksumming inside linear memory rather than asserting it.
11 passBrowser end-to-end tests. Playwright against the real wasm core, not a mock: a markdown note round-trips with matching codes, every offered quality setting completes, portrait and landscape both decode, screen capture decodes with the alignment search skipped, a windowed grab falls back instead of failing, an unreadable source fails fast rather than hanging, and the send view never shows a fake progress state.
S0–S5Six spikes closed with measured results and inspectable artifacts: cell round-trip, degraded-channel sweep, frame integrity, fountain coding across frames, geometry, and the chunked pipeline. Every one is re-runnable by any human. See Numbers.
solidThe screen-capture path. Pixel-perfect frames, no geometry to solve, and it is the path with browser tests behind it.

Not verified

openNo real camera has ever decoded a real screen. Not once. Every optical number in this project comes from a channel simulator. The spike that fixes this — point a phone and a laptop webcam at a displayed frame, save the PNGs, run the same decoder over them — is written up as a ten-minute procedure needing no code, and it has not been done.
unmodelledFrame tearing between an unsynchronised screen refresh and a camera shutter. Prior art suggests frame synchronisation alone can nearly double throughput, so this is plausibly the largest single unknown in the project. A static capture cannot even show it; it needs live video.
unmodelledAuto-exposure and autofocus hunting against a changing image, and screen moiré. The simulator's JPEG stage is also a crude 8×8 block-mean stand-in, not a real DCT.
assumedFrame rate. Every KB/s figure divides a measured frame count by an assumed 15 or 30 FPS. Neither end of that has been timed against real hardware.
unbackedThe screen-capture path's 2.65 MB/s and the camera path's 125.8 KB/s. Reported as the app's own measured figures in the CLI documentation, but no artifact in artifacts/ records them.
What would count as a failure here.

The project's own rule: any divergence between simulated and real symbol error rate is a bug in the simulator, tracked as such — not an excuse and not a footnote. Three outcomes are anticipated in writing. Real worse than simulated means the simulator is too kind. Real better means the weak-camera preset is pessimistic and the rate ladder is leaving throughput on the table. Markers failing entirely would mean they are too small for real optics, and the size clamp is admittedly a guess.

The capture procedure is here — two devices, a room, ten minutes, no code. If you have a phone and a laptop, you can close the biggest open question in this project this afternoon.

Not implemented

missingResume. You cannot resume an interrupted transfer from the app. The receiver displays a resume code and nothing anywhere accepts one — there is no input for it. The machinery underneath exists and works: the core proved it (killed at 71.9%, every retained chunk re-verified off disk, only the missing ones re-sent, byte-identical result) and the WebAssembly layer exposes OpticalReceiver.resume(). It is simply not wired to any user interface. Today, an interrupted transfer starts over.
partialThe manifest is in-band, but only above the core. The core's 25-byte frame header has no room for a manifest and its own pipeline transfers a file only if the receiver was told the manifest some other way — that gap is recorded and still open. The WebAssembly layer closes it in practice by broadcasting the manifest as a pseudo-chunk (a reserved sequence number, fountain-coded like any other chunk: a burst up front, then one frame in twenty-four). So the app works; the core alone still does not.
partialThe layered rate ladder. The design is one broadcast carrying coarse and fine layers together, so a good camera and a weak one both finish off the same stream — and the core demonstrates exactly that end to end. The shipped engine does not: it broadcasts one rung at a time, which is why the app asks a human to pick Reliability vs speed instead of adapting on its own.
missingThe validation handshake. A decision was accepted to add a brief bidirectional phase before any data frame — the receiver shows “I can see you, quality Q”, the sender reads it and only then starts, and at the end the receiver flashes “done, you can stop”. None of it is built. It was prompted by a real observation: a hundred-byte note was broadcast 2,405 times over 40 seconds because the sender had no way to learn it had been received on frame three. Today the sender is still blind and still loops forever, and the app says so plainly rather than faking a progress bar.
missingAn npm release. The CLI package is named and versioned but has no publish step in CI and no release cut, so npx lightpipe does not resolve. Build it from the repository.

Hard limits you will hit

maximum file size the app accepts512 MB — and that is a ceiling, not a target. The frozen WebAssembly contract takes the whole file as one array, so a streaming send cannot be expressed yet. The app refuses larger files with that explanation rather than failing obscurely

What this means for you

Use it today for what it is tested for: small, valuable payloads, with the receiving side a screen capture where you can arrange one, and a careful comparison of the six-character code at the end. That path has browser tests, a zero-false-accept integrity measurement behind it, and no unmeasured optics in the way.

Treat the camera path as promising and unproven. It is thoroughly simulated and not yet observed. If you point a real camera at a real screen and it works, that is new information this project does not have; if it does not, that is a simulator bug worth reporting.
